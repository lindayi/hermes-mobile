# Tool activity lifecycle and Inbox cleanup acceptance

1. Opening a folded tool card deliberately scrolls the conversation to that card's latest tool entry, even if the reader was previously above the bottom. If the expanded card is tall, its latest row must be visible above composer. Collapse does not jump; automatic incoming updates still respect a reader who has scrolled away. Pointer and keyboard activation work, with no cross-route deferred scroll.
2. Card headline/status reflects currently running tool work if any; otherwise the most recent tool entry's state. Earlier failures remain red on their own rows but do not make a recovered list permanently fail. Avoid calling this overall agent/run success; preserve unknown/interrupted semantics. Cover failure→success, failure→running, parallel ongoing with latest completed, and last failure.
3. Restore restrained semantic colors for per-tool success/failure/running and matching heading status, with symbols/text for accessibility and light/dark contrast. Keep ordinary controls monochrome and do not reintroduce blanket emojis.
4. Re-entering a chat shows the latest turn's recorded tool activity exactly once, both active and completed. Trace live production metadata read-only before fixing; distinguish backend snapshot loss/late native persistence, truncation/page boundary, lost journal replay, and frontend dedup/removal. Preserve prior compaction and repeated-prompt protections. Do not rerun tools/model to recover display. Do not rewrite native history.
5. Inbox provides Dismiss on read receipts and a Clear read action with a clear bulk confirmation. Unread messages and pending approvals remain, other users unaffected. Durable cleanup hides receipts without deleting conversations/jobs/native history, maintains ingest deduplication (redelivery must not resurrect dismissed content), and prevents later pending push work for dismissed receipts where feasible; already-sent/in-flight delivery cannot be recalled. Prefer backward-compatible tombstones over destructive data/schema rewrites. Existing read marking remains available. Bulk clear handles all owned read receipts, not merely one visible page.
6. Inbox mutations require existing authenticated user/CSRF boundaries; UI error/pending state is honest and stale completions cannot navigate/update another account/view. No automatic cleanup of live Inbox merely to test it. Synthetic SQLite/API/browser fixtures only.
7. Written cases precede implementation; observe RED→GREEN, verify actual HTTP/SSE/SQLite seams and mobile card geometry/colors, independently review frozen changes. Keep canonical spec synchronized. Full generated-asset tests under actual deployment environment precede guarded activation; no native API/WhatsApp restart, accounts reset, real approvals or job executions.
