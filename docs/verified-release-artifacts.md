# Verified release artifacts (issue #8)

## Scope and trust boundary

The hosted path reuses **one tested public bundle**, not a JSON assertion that CI
passed. A digest or a successful `gh attestation verify` alone does not authorize
release. The existing no-argument controller remains the conservative full-local
build/check path. There is no fallback from failed hosted evidence to skipped
checks, and no flag accepting caller-supplied manifests or evidence.

This work depends on PR #4's `deploy/ci_selection.py`, `scripts/ci_tests.py`, pinned
hosted dependencies and `.github/host-tests.json`. They must be integrated before
using the hosted release path. Its explicit installed-runtime partition runs in
full every time; host evidence is not cached or uploaded.

## CI contract

1. `build` checks out the exact event SHA, builds generated assets once, and runs:
   `python -B -m deploy.release_artifact build --bundle "$RUNNER_TEMP/release.tar"`.
2. The artifact is named `release-${{ github.run_id }}-${{ github.run_attempt }}`.
   Every browser shard downloads that artifact, validates/unpacks it against its
   own checkout with `deploy.release_artifact unpack`, and passes its `public`
   directory to the managed CI runner. Browser jobs never rebuild those assets.
3. The fail-closed `source-ci` aggregate requires `build`, syntax/secret checks,
   JavaScript, both Python shards, all four browser shards and the disposable
   hosted `native` job. Failure, cancellation and skipping cannot satisfy it.
   The native job covers the explicit public-runtime subset; the complete
   installed/private host partition still runs separately at deployment.
4. The always-evaluated `integration-tests` job depends on `source-ci` and succeeds
   only when that complete hosted aggregate succeeds in the same run. Only
   successful `push`/`refs/heads/main` runs in `lindayi/hermes-mobile` reach
   `attest`, which depends on both hosted gates. Only that job has `id-token: write` and
   `attestations: write`. It downloads and attests the exact tar, without checking
   out/running repository code. PRs and manual runs never attest release bundles.
   No deployment credential, SSH key, native evidence or private runtime is
   uploaded. All external actions are full-commit pinned.

A partial rerun cannot reuse an earlier attempt's artifact or jobs. **Rerun all
jobs** when another attempt is required. Artifact retention is seven days;
expired/unavailable artifacts block deployment, not trigger a rebuild.

## Public format and bounds

`release.tar` is an uncompressed tar with regular files only:

- `manifest.json`: exactly `schema: 1`, full 40-character `source_sha`,
  `source_files` (deployable relative names to SHA-256), and `public_files`
  (generated-public relative names to SHA-256).
- `public/<name>`: the exact generated bytes consumed by browser shards.

The source mapping includes every regular deployable file in the controller's
explicit source trees/files, including `.github` so the host partition and CI
contract are frozen. It is a map of public source digests, not a source/private
runtime snapshot. Existing excludes still omit interpreter directories, caches,
config/state/databases and credentials. Symlinked or hardlinked source/public
files are rejected. Stage verification against immutable Git objects remains
independent of these SHA-256 maps.

Downloads/tars are limited to 64 MiB, members to 16 MiB and 10,000 files. GitHub
metadata/verification output is limited to 4 MiB per command, API lists to 1,000
records with checked pagination, and commands to 120 seconds. Linux
`RLIMIT_FSIZE` bounds both subprocess stdout and stderr before buffering. The
transport ZIP must contain exactly one bounded regular `release.tar`; neither
archive is extracted using general-purpose extraction. Tar validation rejects
absolute/traversal/ambiguous paths, duplicates, links, sparse members, devices,
unknown members and schema, incorrect source maps and incorrect public bytes.
All members are checked before any destination files are written.

## Production verification

`acquire_verified_bundle(source: Path, run_id: int, destination: Path,
*, run=subprocess.run) -> VerifiedBundle`:

- Requires the canonical source path and clean freshly fetched exact main using
  the existing Git provenance implementation. No synthetic-source exemption is
  exposed by this API.
- Reads live authenticated GitHub API records on `github.com`. Installed policy
  pins repository `lindayi/hermes-mobile` / ID `1399942965`, workflow
  `.github/workflows/ci.yml` / ID `372155405`, `push`, `main`, exact source SHA,
  completed success and the latest run attempt.
- Requires the exact complete set of successful attempt-specific jobs:
  `build`, `checks`, `js`, `python (0)`, `python (1)`, `browser (0..3)`,
  `native`, `source-ci`, `integration-tests`, and `attest`. Job IDs must be unique;
  missing, duplicate, extra, skipped or previous-attempt jobs fail closed.
- Selects one unexpired exact-run/attempt artifact, validates its repository/SHA
  metadata, downloads by numeric artifact ID and checks GitHub's transport
  SHA-256 when supplied.
- Invokes the real installed `gh attestation verify` with explicit repository,
  exact certificate identity (binding signer repository/workflow) and issuer, main source ref,
  exact source/signer SHA, SLSA v1 predicate and denial of self-hosted runners.
  Certificate identity is the sole signer-identity selector: GitHub CLI rejects
  combining it with `--signer-repo` or `--signer-workflow`. These redundant flags
  are not a stronger policy; the authenticated certificate fields below remain required.
- Checks the verifier's authenticated **certificate extensions**, not the
  workflow-controlled statement predicate, for the exact repository identity,
  push/main/SHA/signer and
  `https://github.com/lindayi/hermes-mobile/actions/runs/ID/attempts/ATTEMPT`.
  Missing `runInvocationURI` or other required extensions is a blocker, never
  grounds for falling back to a predicate string.
- Rechecks the live successful attempt and fresh main after verification, then
  validates the complete source and public mappings before returning immutable
  evidence fields and the public directory.

The controller calls this API itself under its deployment lock. It compares the
source evidence to the already Git-verified frozen stage, copies exact generated
bytes without rebuilding, checks their full mapping again and runs the entire
explicit host partition internally. A caller's `checks` callback is not used to
bypass the hosted residual partition. Existing staged-mutation detection,
protected-native fingerprints, admission/drain, health checks, asset rollback,
service rollback and gate ownership remain in force. Successful status records
include the run/attempt/artifact IDs and bundle SHA-256.

## Approved worker integration

The separate approved-intent pull worker (documented with the pull deployment
components) invokes, in its **own systemd context**:

```text
python -m deploy.self_deploy --hosted-run-id ID
```

This runs synchronously, not through another scheduled transient unit, so the
worker receives the real outcome. `--worker --hosted-run-id ID` also works.
`INVOCATION_ID` is required. Hosted mode rejects frontend-only, bootstrap and
status modes. The ID selects CI evidence, **not approval**: the pull worker must
independently verify the environment-approved intent before invoking it. There
is no production enablement in this artifact implementation.

Keep the no-ID path for explicit conservative full-local validation. Native
controls maintenance also remains operator-authorized, but its normal schedule and
worker path now requires `--hosted-run-id ID`: the scheduler binds that immutable
run ID to its fresh source SHA, and the worker refuses a changed source before
staging or admission. It independently acquires the same exact-main attested
bundle, stages its exact source/public maps through the shared release-stage
verifier, and runs the complete installed-runtime host partition once. It never
rebuilds generated assets or runs the full portable suite on the server in hosted
mode. Missing or invalid hosted evidence blocks maintenance; it does not fall back
to local checks. `--local-full-checks` is a separate explicit diagnostic opt-in for
conservative full-local validation, not routine deployment.

Native status records bind the staged release `git_sha` and validation mode. Only
after successful bundle verification do hosted records also include the exact
source run ID/attempt, artifact ID, and bundle digest. These are local controller
evidence, not a GitHub deployment approval or deployment status.

## Verification and rollout limits

Development tests use fake GitHub/attestation subprocess adapters and synthetic
Git/source/release roots through the managed Python runner. Fake certificates
exercise policy logic; **they are not authentic provenance**. Installed CLI
support and live read-only repository/workflow IDs were inspected, but the first
real issue #8 main artifact does not exist until this reviewed workflow merges
and completes. Before enabling production, verify that artifact with the real
CLI and require the authenticated invocation fields described above. Any
unsupported CLI flag, certificate field, download or API shape blocks rollout;
do not weaken policy to make a synthetic test pass.

PR #4's existing workflow tests must be reconciled to require the additional
`build` aggregate dependency and bundle download/unpack instead of per-browser
`build_frontend`. Keep its suite-completeness, pinned-dependency, isolation and
concurrency assertions. Hosted CI and a reviewed main artifact verification are
still required; focused offline tests do not claim those outcomes.
