# Verified cloud artifacts and guarded pull deployment

Issue #8; part of #5. Approved objective: cloud-first build/test/review, supported local focused development, and approval-gated production delivery without interrupting active runs.

## Trust and acceptance

1. The CI pipeline builds a public release bundle once per exact checkout, uploads it, and every generated-assets browser shard consumes that same bundle. The fail-closed source-ci aggregate requires the build, checks, both Python shards, JavaScript, and all browser shards. Only a successful `push` run for `refs/heads/main` of the allowlisted repository/workflow is release-eligible. PR artifacts are never deployable, including fork PRs.
2. Bundle manifest schema v1 binds full source SHA, regular deployable source file SHA256 mapping and generated-public file SHA256 mapping. No private state, credentials, runtime homes, caches or owner-only paths enter the bundle. Archives reject traversal, absolute paths, duplicate names, symlinks/hardlinks/devices, excess size/files and unknown schema. Git source preflight remains authoritative.
3. Production verification obtains run/jobs/artifacts through authenticated GitHub API and verifies repository identity, trusted workflow path/id, event, branch, exact current main SHA, latest successful attempt and expected complete job set. It verifies archive transport digest where supplied and GitHub provenance attestation with explicit repository/workflow/ref restrictions. A digest/attestation alone never means tests passed. No unsigned local JSON can authorize reduced checks.
4. The release controller stages from canonical clean freshly fetched main, compares bundle source manifest against the actual frozen stage, installs the exact verified generated public bytes, runs only the complete explicit installed-runtime compatibility partition, and retains existing post-check mutation detection, protected-native fingerprints, locks, admission/drain, health checks and rollback. Full legacy local validation remains explicitly available; failed/missing cloud evidence cannot silently skip any gate.
5. Main source CI success creates an approval-gated production workflow. Its protected environment allows main only and requires the owner approval. After approval a minimal contents/actions-read, deployments-write job creates fixed-schema deployment intent containing only exact SHA and successful source-run ID, not executable commands or filesystem paths. The server validates the intent's originating trusted workflow/run and approved job (not merely caller-supplied JSON). Missing approvals or unverifiable provenance fails closed.
6. A separate unprivileged systemd user timer polls outbound; never a production Actions runner or public command webhook. It has an exclusive worker lock and durable per-intent state. Busy/unknown runs, dirty/stale source, ongoing deployment or incompatible native/data changes defer/block without restart. Duplicate/out-of-order/superseded intents do not redeploy. Mid-activation cannot be cancelled. It invokes only the existing guarded controller in its own cgroup and reports real success/failure back to GitHub.
7. Reuse compatible host evidence only if bound to exact source plus installed runtime/dependency fingerprints; otherwise run the residual suite once. Never upload native/private evidence. Initial implementation may rerun the residual suite but must not run all portable suites locally.
8. The ordinary coding/review environment has no deployment secrets or production access. Deployment code, workflow, review-policy changes and migration boundaries retain targeted independent security review. Repository CI text or instructions cannot redefine trusted server policy on their own.
9. Installation/disable/status/rollback are documented and tested with isolated synthetic roots and fake service commands. Tests never exercise production writes. Real enablement occurs only after reviewed merge and inspection; active chat safety may defer actual activation until this request ends. Status must distinguish queued/approval/busy/blocked/deployed.

## Non-goals

No repository transfer, unrestricted webhook, generalized SSH shell, public private-runtime snapshot, untrusted PR checkout in a privileged workflow, forced termination of sessions, destructive database rollback, or removal of local development. Native/runtime/data maintenance remains explicit rather than bypassing existing protection.
