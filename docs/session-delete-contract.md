# Stored session deletion contract v1

This is STANDARD STORED HISTORY DELETE, not all-copy or forensic erasure. Close other clients first: open CLI/native clients may recreate stored history. The mobile tombstone still hides/blocks that ID. Memories, created files, messages on external channels, exports/backups, provider records, notifications and logs are retained. No live deletion is part of implementation/testing.

## Native worker / bridge coordination (stable v1)

- Owner/default dedicated listener only; existing authenticated profile binding. Native feature attestation: `features.mobile_session_delete_version` must be integer `1` (not boolean). Bridge does not call legacy DELETE.
- Native `DELETE /api/mobile/sessions/{exact_id}` JSON exactly `{ "confirm": true, "operation_id": "<server uuid hex>" }`.
- Success JSON MUST include `{ "id": "<exact_id>", "deleted": true, "operation_id": "<same uuid hex>" }`. Additional native metadata is permitted. Browser success is exactly `{ "id": "<exact_id>", "deleted": true }`.
- Native rejects active/unknown work, turn/compression contention, routed/gateway sessions, ambiguous branch/compression identities and unsafe delegate scope. Only exact fixed API/CLI root history is confirmed. Completed delegates may be handled only where native proves the target set without deleting independent chats; native must not silently delete canonical ancestors.
- Non-success (including unbound `deleted:false`, missing/mismatched IDs, 404, timeout, invalid reply) is NEVER browser success. No automatic native DELETE replay.
- **Required read-only receipt endpoint:** `GET /api/mobile/session-deletions/{operation_id}` returns the durable receipt. Auth and owner scope match DELETE. A missing native session alone is not a receipt.
- **Definitive refusal:** native persists `{id:exact, operation_id:exact, status:"refused", deleted:false}` BEFORE returning a safety refusal and only where it proves no deletion committed. The bridge GETs that receipt before releasing its claim. It retains the content-free operation audit record and responds HTTP 409; the unchanged session remains listed/openable. Native must allow a later newly confirmed operation ID after a refused operation, while retaining prior receipts. Bare HTTP 409/404 or `deleted:false` do not release anything.
- On a lost/invalid DELETE response the bridge attempts one read-only receipt lookup: an exact committed success completes the tombstone; exact durable refusal releases it; unavailable/unknown/mismatched receipt remains `native_unknown`. No native DELETE replay. Browser `GET /sessions/{sid}/deletion` may reconcile a persisted pending operation after restart; returns exact `{id,deleted:true}` on committed success, 409 on proven refusal, 503 while unresolved, 404 without a known operation. It does not expose operation IDs or accept client-supplied ones.

## Bridge state/admission

`session_deletions` lives in the RunJournal SQLite writer-lock domain, scoped `(user_id, profile, session_id)` with server-owned operation ID. Claim and run admission use `BEGIN IMMEDIATE`. Claim refuses nonterminal/unknown runs and local workers/controls in the bound profile (including exact IDs and both history anchor aliases). Until native has proved its delegate target set, `prepared`/`native_unknown` operations also pause new run admissions for this owner/profile; otherwise a previously unseen delegate ID could race deletion. This temporary admission pause ends on proved success or refusal, never by clearing an unknown run. Confirmed native receipts include `deleted_ids` when descendants were deleted (maximum 100 safe exact IDs including the root); each receives an owned mobile tombstone together with known local aliases. Tombstones include all proven local aliases of related runs. Foreign owners/profiles are not purged or fenced; same-profile foreign active work also refuses mutation.

State `prepared` is persisted before any native mutation. Transport/reply/refusal ambiguity becomes `native_unknown`; success becomes `deleted` only after exact receipt verification. A crash in `prepared` is unresolved and stays blocked. Repeat browser DELETE while pending/deleted conflicts; a new explicit confirmation after proved refusal may create a fresh operation. Never infer success/reissue an uncertain mutation. `session_deletion_operations` retains content-free operation identity/outcome even when refused claims are released. Every non-released claim blocks list/history/run/control/events/start and keyed run replays. No unknown run is cleared to allow deletion.

Minimal v1 retains scoped journal/audit/key identity behind tombstones instead of promising cross-database content erasure. Native success confirms guarded session/message database deletion, not transcript/request-dump file removal (`files_deleted:false` is allowed). Notification/log copies and completed app journal records may remain stored; direct mobile conversation links/overlays are fenced. No Inbox/email/backup purge. Native catalogue remains read-only. Server errors are content-free.

## Browser

Authenticated owner/default only with strict Origin + CSRF and body exactly `{confirm:true}` (literal boolean; extras rejected). `GET /sessions` advertises `deletion_available:true` only after native versioned capability verification; omitted otherwise for existing-client compatibility. DELETE is once per explicit confirmation. Unknown response must be shown honestly, not optimistically removed as confirmed success.
