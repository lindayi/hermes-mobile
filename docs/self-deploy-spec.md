# Self-deployment acceptance specification

Routine frontend changes should directly replace Hermes public assets without sudo or service restart. Backend bridge changes require a deferred, idle-window release. No broad sudoers rule, no disabling NoNewPrivileges, no permission changes to WordPress, certificates, native Hermes install, private credentials or other profiles.

One-time administrator operation: validate fixed /var/www/html/hermes tree, harden its Apache Directory block to serve only approved static extensions and ignore .htaccess/handlers, grant existing Hermes public tree to lindayi, then drop privileges before invoking bootstrap. Fail before grants on symlinks, nonpublic files or unexpected paths. Disable inherited mod_rewrite only inside the Hermes Directory; retain both no-symlink options. Directory authorization must permit DirectoryIndex resolution at /hermes/ while denying nonallowlisted regular files and directory listings. Tests must use a real Apache child with parent WordPress .htaccess rules, prove both /hermes/ and /hermes/index.html work, and prove parent WordPress routing and private/script/symlink denial remain intact. Apache config changes tested and rolled back on failure. Existing URL/certificate/proxy unchanged.

Frontend publisher cases: build deterministic versioned public assets before checks; stable index.html references versioned modules/CSS/icons/manifest/worker, with all versions derived from the complete source graph. Rewrite local references and worker cache identity; verify generated assets in real browser tests via HERMES_FRONTEND_DIR and freeze them alongside source. Stable HTML must refresh; no guarantee for old open tabs after obsolete assets are removed. Allowlisted assets only; reject all symlinks/path escapes/unsafe backup locations; snapshot prior public files privately with checksum manifest; publish by per-file atomic replace (not a distributed multi-file transaction); remove obsolete assets; restore on failure without touching user data. No private app source/config/state published. Verify exact public landing URL and each asset via actual HTTP/hash checks; a readable index.html alone is insufficient. HTTP failures identify the failing path/status. Both canonical browser and cache-busted URLs must match expected bytes. Retry byte mismatches at most six times per resource with 1/2/4/8/8-second delays within a 90-second aggregate public-check budget; HTTP authorization errors still fail immediately. Never accept stale bytes, weaken TLS verification, or substitute a local-origin success for public serving. Enforce whole-request deadlines with installed curl plus process timeout (including trickling headers/body), reject post-deadline success, and bound returned data by expected asset size. Transport read timeouts may retry within the same budget. Direct file update does not reload any service.

Bridge controller cases: tests gate release; copy reviewed source into private immutable-per-release directories; preserve workspace; gate new run admission atomically while existing runs drain; unknown runs block; deferred systemd worker survives current response; no native/WhatsApp restart. Switch bridge code only while idle, health-check plus auth denial and assets, roll back previous code/assets on failure but never DBs. Refuse dependency/native patch drift requiring operator upgrade. Bootstrap migration from old un-gated bridge is an explicit operator maintenance window. Retrying a rollback_failed initial bootstrap may recover only under the deployment lock: require no current/drop-in pointer, exact recorded gate owner, no active/unknown runs, existing DB, validated private backup manifest and matching restored files, then healthy expected source process/auth denial/public landing+asset verification. Recheck state/assets under a writer transaction before clearing only that gate. Failure preserves diagnostics/gate; never force-unlock or restore user DBs. Ordinary releases cannot erase a failed-rollback record.

Testing: observe RED then GREEN for each slice, temp fixture paths only, injected process/health boundaries for systemd/root tests. Real local HTTP publisher verification required. No live credential reads, account probes, real model runs or service restarts during implementation. Final operator setup is necessary because current process cannot elevate/write root-owned public assets.
